# Two writers in one worktree: a claim both agents win, an id two issues share

Every write is read-validate-modify-write with nothing serialising it, so two
processes in the same worktree interleave and one of them loses silently.

## A claim two agents are both told they won

`try_claim` writes and then reads back, on the reasoning that whichever order
two writes land in, exactly one caller reads its own name back. That holds when
the two writes are adjacent. It does not hold when a third operation fits
between a writer's write and its read-back - which is what its own `ponytail:`
note already says is still open. Forced, with no change to its logic:

    try_claim said: {'alice': True, 'bob': True}
    actual owner on disk: bob
    VERDICT: BOTH TOLD SUCCESS

Alice was told the issue was hers and starts work on it. Bob owns the file.
This is precisely the outcome `next --claim` exists to prevent, and it reports
success while failing.

## Two creates, one id, one issue gone

`next_id` scans the directory for the highest id and `write_issue` writes it.
Between those two steps another process can allocate the same number:

    ids allocated: ['ISS-001', 'ISS-001']
    files on disk: ['ISS-001.md']
      ISS-001.md -> Alice's report
    VERDICT: COLLISION - one issue lost

Both creates printed "has been created". Bob's issue never existed.

`next_id` carries a `ponytail:` note about this, but it scopes the problem to
concurrent worktrees and leans on git making the collision loud as an add/add
conflict. Two processes in one worktree get no such signal: there is one file,
one blob, and nothing for git to conflict about. The note understates it.

## The fix

A lock around the whole read - validate - modify - write, not around the write
alone: atomic replacement (ISS-038) stops a torn file, but two well-formed
writes racing is a different failure and ordering them is the only answer.

Id allocation needs the stronger version - create the file with `O_EXCL` so the
loser gets `FileExistsError` and retries with the next number, rather than
asking who is highest and hoping.

A lock file under `.issues/` is the obvious mechanism and needs a stale-lock
story: a killed process must not wedge the tracker for everyone after it.

Blocked on ISS-038 only in ordering, not in scope - the durable write is the
floor this builds on.

## Acceptance

- two concurrent claims: exactly one is told it succeeded, and it is the owner
- two concurrent creates: two ids, two files, no lost issue
- a killed process does not leave a lock that blocks the next command forever
- single-process use pays no noticeable cost - this tool is run from a prompt
- tests that force both interleavings rather than relying on timing luck
