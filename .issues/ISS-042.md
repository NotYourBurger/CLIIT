# issue check calls four kinds of broken file healthy

`issue check` is the doctor for the format that is the API. Four deliberately
broken files in one directory, and it reports nothing at all:

    $ issue check --json
    []
    exit 0

The four, and what each one actually costs:

**A missing required field.** `parse_issue` requires id, status, created_at and
title, and returns None without one. That skip is correct for a stray note in
the directory - it is what keeps `notes.md` out of `issue list` - but a file
named `ISS-001.md` is not a stray note. It vanishes from `list`, from `next`,
from every count, and `check` never says so. Confirmed: the planted ISS-001 is
absent from `issue list` entirely.

**A dependency cycle.** `require_blockers` refuses to write one, using
`cycle_from` from `deps.py`. `check.py` never imports it. A cycle that arrives
by hand-edit, by merge, or by the write race in ISS-039 is permanent: both
issues show as blocked by each other, neither can ever be ready, and nothing
ever says why. The check is one call to a function that already exists.

**A filename that disagrees with the id inside it.** `ISS-050.md` containing
`id: ISS-777` lists as ISS-777 and reads fine, but `issue log ISS-777` looks
for `ISS-777.md` and finds nothing. `check` already tracks `file_by_id` to
catch duplicate ids and has both halves in hand; it just never compares them.

**Evidence that is not valid JSON.** `evidence` is the one field holding JSON
rather than a comma-joined string, and nothing ever confirms it parses. A
closed issue whose evidence is malformed is a closed issue whose proof cannot
be read - which is the one thing this tool refuses to close without.

## The shape of the fix

These are all the same omission: `check` verifies that a file survives a
rewrite and that blockers exist, and asks nothing else. Each addition is a
question the codebase can already answer - `cycle_from` exists, `file_by_id`
exists, `json.loads` is already imported.

The `parse_issue` case needs care and is the only one with a design decision
in it: the skip is load-bearing for non-issue files. The distinction is the
filename - a file matching the id shape that fails to parse is a finding, a
file that does not match is not.

ISS-034 deliberately declined to add a cross-field finding, on the grounds
that no file on disk had the problem and one fix at the write covered every
path in. ISS-041 shows a path that was not covered, which is the condition
ISS-034 named for revisiting it.

## Acceptance

- a file whose name matches the id shape but does not parse is a finding that
  names the missing field
- a dependency cycle is a finding that prints the path, as `require_blockers`
  already does
- a filename that disagrees with its id is a finding
- evidence that is not a JSON array of objects is a finding
- a stray non-issue .md file in `.issues/` is still not a finding
- the real `.issues/` still passes clean
