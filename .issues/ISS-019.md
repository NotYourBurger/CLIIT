# issue next - the one issue to work on now

`issue list --ready` answers "what could I work on", and then hands back a
table and leaves the last step to you. For a person that is fine, the eye picks
the bottom row. For an agent it is five calls and a paragraph of context: list,
read the statuses, read the priorities, chase the blockers, decide - every time,
before it has done any work at all. The decision is already deterministic and
already ours; making every caller re-derive it is the waste.

```
issue next            # the one issue to work on now
issue next --json     # the same decision, for an agent
```

One issue out, read-only, exit 1 when there is nothing to start.

## The rank is the whole feature

Candidates are issues that are neither closed nor blocked, ordered:

1. `in-progress` before `open` - work already started is work you are about to
   abandon, and abandoning it is the failure this ordering exists to prevent
2. priority high, medium, low, then unset
3. oldest `created_at`
4. id

The tail of that list is not decoration. Two issues filed the same minute with
the same priority have to come out in the same order on every call, or an agent
asking twice gets told to do two different things and neither gets finished.
`created_at` then id is what makes "identical state, identical answer" true
rather than approximately true.

Note it is `rank` reversed, plus two terms. `rank` sorts least-urgent-first
because the table reads bottom-up; `next` wants the other end. Same tuples,
read the other way - not a second opinion about what urgent means.

## `--ready` is not the predicate this needs

`is_ready` is `status == "open" and nothing in the way`, and that is right for
the filter it was written for. `next` wants the same blocker rule over a wider
status set, because a ready `in-progress` issue is the first thing it should
return and `is_ready` says no to all of them.

So the split is: `in_the_way` is the source of truth, and it already is -
`is_ready` is that call plus a status test, and `next` is that call plus a
different one. What must not happen is `next` growing its own idea of blocked;
two functions that both decide what blocks work is how the tracker starts
recommending work it also refuses to list.

## Ready, in the output

Human output is the row, not a table:

```
ISS-014  Fix dependency cycle detection
Status:   open
Priority: high
Ready:    yes
```

`Ready: yes` is the only line that is not a transcript of the file, and it is
the one worth printing - it is the claim the command is making. It is always
`yes`, because a `no` would be a bug rather than a result, and printing it
anyway is what makes that visible if it ever happens.

`--json` is the existing `as_dict` for one issue, one object, not an array of
one - the caller asked for the next issue and got the next issue. Nothing else
on stdout in either mode.

## Nothing to do

Empty backlog, everything closed, everything blocked - all the same answer:
a sentence on stderr and exit 1. Not exit 0 with a null, because the shell
already has a word for "I have nothing for you" and a script that checks
`if issue next --json > pick.json` should take the other branch. JSON mode
prints nothing at all on stdout, so a parser reading it gets a clean EOF
instead of a prose apology wearing a `{}`.

## What it does not do

It does not claim, does not set `in-progress`, does not touch a file. `claim`
is one call away and it is the caller's decision; a `next` that silently
assigned would mean you cannot ask the question without answering it. That is
also what keeps it cheap to call twice.

Also out: `--label` and `--assignee` narrowing, due dates, anything that reads
the description. The last one is the line - no ranking that a person cannot
reproduce by looking at the frontmatter.

## Where it touches the code

`select_issues` already loads, filters and sorts; `next` is that loop with the
blocked ones dropped, a different sort key, and `[0]`. The ranking belongs next
to `rank` and away from `print_table`, so the same selected issue feeds both
outputs - one decision, two renderings.

## Open

`--label backend` is the first extension anyone will ask for and it costs a
parameter, since `select_issues` already takes labels. Leaving it out of the
first cut on the grounds that a filter on `next` is a different question -
"what should I work on in this area" - and worth naming once someone actually
asks it out loud.
