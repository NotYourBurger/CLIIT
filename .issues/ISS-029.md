# issue close - --verified alone is not proof of completion

A review read this as "close accepts evidence nobody checked". That is wrong and
worth writing down: `require_commits` runs `git cat-file -e <sha>^{commit}`
before the write, so a `--commit` that names nothing exits 1 with the file
untouched. `--pr` needs a network and `--test` is recorded rather than run, both
deliberately - a tracker that shells out because a flag said so is a different
and much worse tool.

What is left is one loophole. `close --completed --verified "looks fine"`
satisfies the evidence rule with an unfalsifiable sentence, sitting next to a
field that is machine-checked. Half-enforced is the worst rung.

Two ways, and (a) is the recommendation:

**(a) Warn and close anyway.** Evidence that is only `verified` gets one stderr
line naming it unverifiable. This is exactly how `close` already treats unticked
checkpoints: the divergence is made visible and nothing more.

**(b) Require one machine-checkable item** - `--commit` or `--test` - for
`completed`. Real teeth, and it breaks `tests/helpers.py:close()`, which uses
`--verified` on purpose so the fixtures are not tied to whatever repo they run
inside.

That collision is itself the argument for (a): this repo's own suite is a
legitimate case for evidence a machine cannot check.

**Decision needed before this is started.**

## Acceptance

- verified-only close still exits 0, with the warning on stderr and not stdout
- evidence with a commit or a test alongside warns about nothing
- every existing close path prints the same stdout it printed before
- `tests/test_close.py` covers each, and `tests/all.py` passes untouched
