# Split issues.py along its existing seams

`issues.py` is 1441 lines and about fifty functions, and `cli.py` imports ten of
them. The other forty are the machinery those ten stand on, and every one of
them is now read by scrolling past the other thirty-nine.

CLAUDE.md says the file is one large file on purpose, and that stays true for
the reason it was written: `list`, `next`, `brief`, `search`, `view`, `set`,
`close` and `claim` share their filtering, their blocking rule and their
ordering, and splitting them into a module per verb would give each verb a
private copy of an opinion the repo has exactly one of. That is not what this
asks for. Splitting per verb is the wrong cut and stays rejected.

The cut is the other way: the layers under the verbs. There are four of them,
they already exist, and CLAUDE.md's own architecture section is a list of them -
which is the tell that they are real boundaries being held in prose because
they are not held anywhere else.

## The seams

Each of these is a contiguous run of `issues.py` today. This is a move, not a
redesign.

- **`fields.py`** - reading one parsed issue: `priority_of`, `assignee_of`,
  `current_user`, `set_field`, `labels_of`, `blockers_of`, `evidence_of`,
  `resolution_of`, `evidence_label`. Pure functions of a dict. No disk, no
  printing. This is where the "absent means absent" rule lives, and it is
  currently interleaved with code that has nothing to do with it.
- **`deps.py`** - `blocker_status`, `said_blockers`, `in_the_way`, `is_ready`,
  `actionable`, `blocks`, `blocked_note`, `cycle_from`. This is the seam worth
  the most. CLAUDE.md already says `in_the_way` is the only function that
  decides what blocked means and that a third opinion must not grow; a module
  boundary enforces that where a comment only asks for it. Anyone adding a
  blocking rule now has to open the file that owns blocking.
- **`validate.py`** - `clean_set`, `clean_labels`, `clean_ids`,
  `require_status`, `require_priority`, `require_blockers`, `require_commits`.
  The "validate before writing" convention, in one place, with the comma rule
  that the whole file format depends on stated once at the top of the file that
  enforces it.
- **`render.py`** - `THEME`, `console`, `COLUMNS`, `print_table`, `describe`,
  `next_lines`, `brief_rows`, `resolved_lines`, `omitted`, `as_dict`. Everything
  that turns issues into characters. `rich` gets imported here and nowhere else,
  which makes "stdout parses, stderr explains" auditable by reading one file
  instead of grepping for `print`.

What is left in `issues.py` is the ten command functions plus `load_issues`,
`select_issues`, `matches`, `matching_lines`, `narrowing`, `ranked_actionable`,
`rank`, `next_rank` and `closed_key` - the single filter path and the single
ordering, which are shared behaviour and belong together for the reason the
file was one file in the first place. It ends around 700 lines and every line
in it is a decision about issues rather than plumbing under one.

## The rules the move has to hold

- **Pure move.** No renames, no signature changes, no "while I'm here". A
  reviewer must be able to check this by reading the diff for lines that are
  not identical to lines that left. Anything worth changing gets its own issue
  and its own commit after this one lands.
- **Imports go one direction.** `storage` -> `fields` -> `deps` -> `validate`
  -> `render` -> `issues`. Nothing imports `issues`; if something wants to, the
  thing it wants is in the wrong module. A cycle is not a style problem here,
  Python raises on it and the whole suite fails at import, which is a fine
  check to have for free.
- **`cli.py` does not change.** `issues.py` keeps importing the names it moved
  out, so every `from cli_issue_tracker.issues import ...` still resolves. The
  entry point is not part of this refactor and should not appear in the diff.
- **No new tests.** `tests/all.py` passing unchanged is the entire acceptance
  criterion, and it is a strong one: a pure move that breaks nothing is a pure
  move that changed nothing. Writing a test for a refactor that adds no
  behaviour is the thing the test suite is there to make unnecessary.
  `tests/test_encoding.py` walks the repo rather than a file list, so the new
  modules are covered the moment they exist.
- **The comments move with their code.** The prose in `issues.py` records
  rejected alternatives and it is the most valuable thing in the file. It is
  attached to functions, not to line numbers; strip none of it, and the
  paragraphs that explain a whole group become that module's docstring.

## What this is not

Not a package restructure - `src/cli_issue_tracker/` stays flat, five more
modules beside `storage.py` and `convert_id.py`, no subpackages. Not a
behaviour change of any kind. Not an interface with one implementation, not a
registry of commands, not a base class for anything. And not a rule that files
must be small: this splits the four layers that already have names, and the
next file that grows earns its own argument.

Commits: one per module, in import order, suite green after each. Five small
diffs that each move one thing are reviewable; one 1400-line diff is not, and
a pure move that nobody can review is indistinguishable from a rewrite.
