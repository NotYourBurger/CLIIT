# issue renumber: repair a collided id, with a journal

Once two files carry the same id, nothing repairs it. Resolving the add/add
conflict by renaming one file strands every reference to it: other issues'
`blocked_by`, the `duplicate-of` / `superseded-by` ids inside the `evidence`
JSON array (issues.py:1042-1043), `work/ISS-NNN.md`,
`work/ISS-NNN.events.jsonl`, and the commit prefixes. `check` reports some of
it; a human fixes all of it by hand.

`issue renumber OLD NEW`, with `--file PATH`.

`--file` is not optional polish. After an add/add resolution both files
contain `id: OLD` while only one can be named `OLD.md`, so OLD alone does not
identify a file. Unambiguous (one file claims the id) runs the full
transaction; ambiguous refuses and lists the candidates until `--file` picks
one.

References in the ambiguous case are not decidable by the tool. When two files
claim ISS-006 and a third says `blocked_by: ISS-006`, which one it meant is
unknowable. So:

- Unambiguous: issue file, `blocked_by` and evidence refs, work plan, event log.
- Ambiguous (`--file`): the selected issue file only.

The plan and event log are equally unattributable, so they stay put too. The
command reports loudly what it did not touch and points at
`issue set --blocked-by/--unblock`. Refusing to guess beats a confident wrong
rewrite - the call `close` already makes when it warns and writes anyway.

Prose mentions of OLD in bodies and plan text are reported, never substituted:
a blind pass over free text mangles an issue that merely quotes an id.

## The journal

Renumbering is a multi-file transaction; per-file atomic writes and a lock do
not survive a crash halfway through. `.issues/.renumber.json`, written via
`write_atomic` before anything is touched and removed on success:

```json
{ "from": "ISS-006", "to": "ISS-007",
  "file": "second-copy.md",
  "steps": ["issue", "refs", "plan", "log"],
  "done":  ["issue"] }
```

Steps, each idempotent, recorded in `done` as they complete: `issue` (write
the new file with the new id, remove the old), `refs`, `plan` (move and fix
the `# OLD Work Plan` heading), `log`. `--resume` replays what is not done;
`--abort` inverts what is, in reverse. `renumber` refuses to start while a
journal exists, and `issue check` reports one as a finding - rather than every
command paying a journal check on every run.

The journal is committed, not gitignored like `.issues/.lock`: the
half-finished state it describes lives in files that are committed, so a
collaborator who pulls mid-transaction gets the explanation with the mess.

Lives in `issues.py` because it needs `load_issues()` (issues.py:157);
`check.py` and `convert_id.py` each already own a listdir and a third copy is
the duplication the layering rule exists to prevent. `close_issue` is the
precedent - a write verb that reads every issue first. Runs inside one
`storage.locked()`, which is not reentrant.

## Acceptance

- unambiguous renumber moves file, plan, event log and rewrites `blocked_by`
  and `duplicate-of`/`superseded-by` evidence refs
- ambiguous is refused with the candidates named; `--file` moves that file
  only and reports what it left alone
- prose mentions are reported, not rewritten
- a refused renumber writes nothing
- interrupting after each of the four steps: `check` names the pending
  journal, `--resume` completes, `--abort` restores
- `tests/test_renumber.py`
