# Issue Priority

Nothing on an issue says which one to do first. The list sorts by status and
then by id, so a typo report and a data-loss bug sit next to each other in
whatever order they were filed.

```
issue create "Login bug" "..." --priority high
issue list --priority high
```

## Scope

- `priority` in the frontmatter, one of `high`, `medium`, `low`
- `--priority` on `create`, defaulting to `medium`
- `--priority` on `list`, filtering, and a PRIORITY column in the table
- A bad word exits 1 and names the three, before touching the disk - same
  contract as `require_status`
- The thirteen issues already on disk have no `priority` field. They must keep
  listing. Missing is not `medium`: nobody set it.

## Design notes

`write_issue` already carries unknown frontmatter keys through a rewrite, and
`parse_issue` already puts every key it finds in the dict, so the field costs
no storage work at all - only `create` writing it and `list` reading it.

`require_status` and `STATUSES` are the pattern to copy: one tuple, one
validator, shared by the command that filters and the command that writes.
Adding a near-identical `PRIORITIES` and `require_priority` next to them is the
lazy version; generalising both into one parameterised validator for two
three-word lists is not worth it yet.

## Open questions

Does priority change the sort? Status-then-id is the current order and is
predictable. Sorting high above medium inside each status group is one more
term in `rank` and probably what people expect from the word "priority" - but
it makes the list order depend on a field most existing issues do not have.
Filtering only, sorting later, is the smaller first move.

How does an existing issue get a priority? `issue set` only takes a status.
Either `set` grows a `--priority`, or there is a separate command, or the
answer for now is "edit the file" - which is a real answer in a tracker made of
files, and the one this issue assumes until asked otherwise.
