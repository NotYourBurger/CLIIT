# Reopening an issue must drop the resolution it no longer has

There is no `reopen` verb, and there does not need to be - `issue set ISS-NNN
open` is the path. But it currently leaves the close behind. Run against a
copy of ISS-031:

    $ issue set ISS-031 open
    ISS-031 has been set to open

    id: ISS-031
    status: open
    ...
    reason: completed
    closed_at: 2026-09-07T15:18:58+06:00
    message: issue check --plans reports commits, staleness and ticked per plan
    evidence: [{"type": "commit", ...}, {"type": "test", ...}]

An open issue carrying proof that it was completed. `issue check` does not
flag it, `resolution_of` reads it back happily, and `issue view` will render a
Resolution block on an issue nobody has resolved.

For a tool whose one enforced rule is that closing takes evidence, this is the
file format lying in the exact place it promises not to.

## The fix

At the write, not the read. In `set_fields`, when the status being written is
not `closed` and the issue on disk is, pop `reason`, `closed_at`, `message`
and `evidence`.

The precedent is already in `close_issue`, in its own words: "Overwrite, not
append: closing a reopened issue replaces the old resolution rather than
growing a list. The previous one is in git and `issue log` already prints it."
Same answer, same reason - this is the other half of the same rule, and the
half that was missed.

## Deliberately not a check finding

`check` holds no cross-field consistency rules at all, and no file on disk has
this problem today. One fix at the write covers every path in. Add the finding
if a hand-edited file ever produces one.

## Acceptance

- reopening a closed issue clears all four resolution fields
- an issue closed before those fields existed is untouched - absent stays absent
- closing again writes a fresh resolution, as it does now
- test_close.py covers close -> reopen -> inspect
