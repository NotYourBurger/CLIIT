# Full-text search across titles and bodies

Fourteen issues fit on a screen. Forty do not, and `issue list | grep` only sees
what the table prints - the title. Everything you actually wrote is in the body,
which is the part no command searches.

```
issue search "verification email"
issue search "clerk" --status open
issue search "auth" --priority high
issue search "email" --label bug
issue search "verification" --json
```

## The whole lifecycle

1. **Query** - one positional string, required. No query is an error, not a
   listing of everything: `issue list` already does that.
2. **Match** - the words of the query, all of them, case-insensitively, as
   substrings, against the title and the body.
3. **Narrow** - `--status`, `--priority`, `--label`, all optional, all ANDed
   with the query and each other.
4. **Show** - the same table `list` prints, plus the line the match came from.
5. **Pipe** - `--json` for scripts and agents, and an exit code that says
   whether anything matched.

## Matching

Split the query on whitespace and require every word, case-insensitive,
substring, anywhere in the title or body. `"verification email"` finds
"verification of the email" - a phrase search would not, and getting nothing
back for a query whose words are all in the file is the failure people give up
on a search box over.

Substring, not word-boundary, so `auth` finds `authentication` and `oauth`.
That is the behaviour of every editor's find, which is where the expectation
comes from.

Not in scope, deliberately: regex, fuzzy matching, stemming, ranking by term
frequency. Each is a real feature and none of them is what "find the issue
about the verification email" needs.

Searching the body means reading every file - which `list` already does on
every run. At forty issues that is nothing. It stops being nothing somewhere
north of a few thousand, and the answer then is an index, not a faster scan.

## Order, and the shape of the result

Same order as `list`: least urgent first, highest priority nearest the prompt.
Not relevance-ranked. Two different orders in one tool means reading the same
ids in two arrangements and having to notice which command produced them, and
the ordering the list already uses exists for a reason that does not stop
applying because the rows were filtered by a word.

Same columns as `list`, too, and the same conditional LABELS column. The
sketch that started this issue had `ID PRIORITY STATUS TITLE`; making search
results look like list results is worth more than getting the columns in the
order they were first imagined.

What search should add is the thing `list` cannot show: **the line the match
came from**, indented under the row, for matches that are in the body rather
than the title. That is the difference between "here are four ids" and "here is
why each of them matched" - and it is the only part of this issue that is not
already solved by filtering.

## Agent experience

An agent runs `issue search`, reads stdout, and decides. That means:

- `--json`: the same array `list --json` prints, plus, per issue, the matching
  lines. An agent that has to re-read the files to find out why something
  matched has been given a worse tool than `grep -n`.
- **Exit 1 when nothing matched**, `--json` or not. This is `grep`'s contract,
  and search is a grep-shaped command: `issue search "verification" || issue
  create "..."` should work. It differs from `issue list open` printing "No open
  issues" at exit 0, and the difference is defensible - a filter finding nothing
  is a fact about the repo, a search finding nothing is a failed lookup, the
  same way `view` on a missing id is.
- No color, no box drawing, one issue per line, ids first: whatever reads it,
  human or `awk`, gets the same thing.
- The empty case says what was searched for, on stderr, so stdout stays parseable.

## Where it touches the code

`list_issues` already filters by status, priority and labels. Search needs the
same three filters plus a query, and two copies of that filtering will drift
the first time a fourth field is added. One selection function taking all four,
shared by both commands, is the change - and it is the same seam as the field
table this codebase will want if a fifth field ever lands.

`--status` on `search` is a flag, because the query is the positional argument
and a bare trailing status word would be a query word. `issue list open` should
grow `--status open` as an accepted spelling for the same reason: the two
commands should not disagree about how you name a status.

## Open

Should `search` match ids too, so `issue search ISS-014` finds the issue rather
than the issues that mention it? `view` already takes an id, and an id in a
query is almost always someone looking for the references. Leaning no.
