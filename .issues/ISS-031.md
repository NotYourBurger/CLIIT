# issue check --plans - the number that decides whether work plans survive

ISS-026 shipped the work plan on an argument, and put the risk on the record in
its own words: nothing enforces this, and a seeded plan that is never ticked is
worse than no plan because the next agent believes it. The handover before it
died on exactly that, and it took twenty-five issues to notice - because nobody
was counting.

So count. Git already holds the answer, since a plan is a file in the repo.

`issue check --plans` reports, per plan:

```
ISS-026  3 commits   last touched 2 commits ago   4/6 ticked
```

- **Edits**: `git log --follow --oneline .issues/work/ISS-NNN.md`. A plan with
  exactly one commit was seeded and never touched again. That is the handover
  failure with a number on it.
- **Staleness**: commits to HEAD since the plan last changed, while the issue is
  still in-progress. A high count is a plan confidently lying to whoever reads
  it next.
- **Ticked**: from `read_plan`, which already parses this.

A git failure costs the block and not the command, the call `git_context`
already makes.

## The threshold, written down before the result is known

After the next **five** issues worked through `issue start`: if fewer than three
of five plans show more than one commit, the work plan is deleted the way the
handover was, and `docs/PRD/05-Work-Plan.md` records why.

Baseline today: one plan on disk, zero commits.

Putting the number here rather than in a habit is the whole point. The previous
answer to this question was a sentence in a file, and a sentence in a file is
what produced zero handovers.

## Acceptance

- a seeded-never-edited plan is reported as such
- ticked counts match the file
- git-dependent assertions stay loose where there is no repo, the way
  `require_commits` skips when there is no git dir
- `tests/test_check.py` covers each
