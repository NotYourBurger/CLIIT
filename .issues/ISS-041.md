# start writes status and assignee directly, past every rule the other verbs keep

`start_issue` sets `status` and `assignee` with `write_issue` directly. It is
the only verb that writes either field without going through the code that
holds the rules about them, and it disagrees with every other verb as a result.

One run, as bob, against an issue closed by alice:

    $ issue claim ISS-001
    ISS-001 is closed - there is nothing to claim          (exit 1)

    $ issue start ISS-001
    ISS-001 is in progress - plan at .issues/work/ISS-001.md

    status:   closed      -> in-progress
    assignee: alice       -> bob
    reason:   completed   -> completed
    closed_at: <alice's>  -> <alice's>
    evidence: [alice's suite] -> [alice's suite]

Three separate rules broken by one call:

**Ownership.** `claim` is described as the one ownership verb that can fail,
and it refuses this exact operation one line earlier. `start` takes the issue
off alice with no check and no mention. An agent running `start` on a
mis-typed id silently reassigns someone else's work.

**Reopening.** A closed issue becomes in-progress with no deliberate step. That
is a real transition, but it should be one the caller asks for.

**The stale resolution.** This is ISS-034 reaching only half its cases.
ISS-034 fixed reopening to clear `reason`, `closed_at`, `message` and
`evidence`, and its write-up made the call explicitly: "At the write, not the
read. In `set_fields`" and "One fix at the write covers every path in." That
was true of every path that existed to be covered - `set_fields` really is the
only other writer of `status`. `start_issue` calls `write_issue` itself and
never enters `set_fields`, so it never sees the clearing.

The result is the exact file ISS-034 was filed to make impossible: an issue
that is in-progress and carries proof that it was completed. `issue view`
renders a Resolution block on it, and `issue check` holds no cross-field rule
that would notice.

## The fix

Not a fourth copy of the rules in `start_issue`. The reopen-clearing and the
ownership precondition each already have exactly one home - `set_fields` and
`claimable_by` - and the bug is that one writer routes around both. Route
`start`'s status write through the same path the other verbs use, so a rule
added there is a rule `start` gets.

Reassignment should be deliberate: refuse an issue that is someone else's and
name the owner, the way `claim` does, with a flag to take it anyway.

## Acceptance

- `start` on another person's open issue is refused, naming the owner
- an explicit flag reassigns it, and says that it did
- `start` on a closed issue either refuses or reopens it cleanly - never
  in-progress with a resolution still attached
- reopening through `start` clears the same four fields `set` clears
- `start` on your own or an unassigned issue is unchanged
- test_plan.py covers close -> start -> inspect, the mirror of the
  close -> reopen -> inspect case test_close.py already has
