# Find .issues by walking up, not from the current directory

The tool only works from the repo root.

```
$ cd src/ && issue list open
Please Run - issue init - to initialize the project first     (exit 1)
```

`issues_dir()` resolves `.issues/` as `os.getcwd() + "/.issues"`, so one `cd`
into a subdirectory and the tracker is gone. This is a defect, not a
convenience gap - every other repo-scoped tool walks up: git for `.git`,
cargo for `Cargo.toml`, npm for `package.json`.

## The trap behind it

Run `issue init` from `src/` to "fix" the error and you now have two `.issues/`
directories. Both allocate ids independently, so both will hand out `ISS-012`.
Nothing warns you, and the two halves of the tracker never see each other.

## Scope

Walk up from the current directory to the filesystem root looking for a
`.issues/` directory. Roughly six lines, all inside `issues_dir()` - every
command inherits it, because they all route through `require_issue_dir`.

`init` is the exception and must NOT walk up. `issue init` means "make one
here". It should warn if it finds an existing `.issues/` in a parent rather
than silently creating a second tracker.

## Ride-along, worth doing in the same change

An `ISSUES_DIR` environment override, checked before the walk. One line, and
it is what lets `test_storage.py` stop doing `os.chdir` into a temp directory
just to avoid writing over the real `.issues/`.

## Relationship to ISS-005

ISS-005 is really two issues: "the ISS- prefix is hardcoded" and "where issues
live is hardcoded". This one resolves the second half. Re-read ISS-005
afterwards - what remains should be smaller and sharper.

## Edge cases

- No `.issues/` anywhere up to the root: current message and exit 1 are right
- Stop at the filesystem root, not an infinite loop on `dirname("/")`
- Decide whether to stop at a `.git` boundary or keep walking past it
