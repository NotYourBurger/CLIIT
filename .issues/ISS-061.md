# check validates both duplicates, not just the last

`check` does report two files carrying the same frontmatter id - ISS-035 built
that and `tests/test_check.py:209-223` pins it. What it does not do is check
them both.

`by_id[issue["id"]] = issue` (check.py:256) is keyed by id, so the second file
of a duplicate pair overwrites the first. Pass B - unknown status, unknown
priority, dependency cycles, dangling `blocked_by`, unreadable evidence - then
runs over the survivor only. Every problem in the other file is invisible, in
exactly the situation where a file is most likely to be wrong: one that
arrived through a merge conflict somebody resolved by hand.

Key Pass B by filename and carry the id alongside, so both files are validated
and each finding names the file it came from. The duplicate-id finding itself
is already right and stays.

Two findings to add while in here, both the same shape of silence:

- an `evidence` item of type `duplicate-of` / `superseded-by` whose id is not
  here. `unreadable_evidence` (check.py:95) validates the shape and never that
  the reference resolves - the same hole as a dangling `blocked_by`, which is
  already a finding two lines above.
- a `.issues/.renumber.json` on disk, an interrupted renumber (ISS-060).

All three reuse the `(name, problem)` tuple, so the promised
`[{"file","problem"}]` JSON and the 0/1 exit codes are unchanged.

## Acceptance

- two files sharing an id, where the first has a bad priority: both the
  duplicate finding and that priority finding are reported
- a `duplicate-of` naming an id that is not here is a finding; one that
  resolves is not
- a pending renumber journal is a finding
- `--json` shape and exit codes unchanged
- cases added to `tests/test_check.py`
