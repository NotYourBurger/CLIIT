# Evidence-based closing - what was done, and where is the proof

`issue set ISS-014 closed` records one fact: someone considered this finished.
It does not say what was done, how it was checked, or where the code is. Every
one of those is recoverable today - `issue log` gives the commits, the diff
gives the change - but recovering them is a research task, and the person doing
it months later is usually an agent with no memory of the session that closed
the issue. The tracker already holds the plan; the point of this is that it
should hold the outcome too, in the same file, at the moment it is still known.

PRD: `docs/PRD/02-Evidence-based-closing.md`.

```
issue close ISS-014 --completed -m "..." --commit 81af03c --test "uv run python tests/all.py"
issue close ISS-018 --not-planned -m "Conflicts with the deterministic search contract."
issue close ISS-028 --duplicate-of ISS-014 -m "Same bug."
issue close ISS-022 --superseded-by ISS-031 -m "Replaced by the architecture index."
```

## Four reasons, and the one that costs something

`completed`, `not-planned`, `duplicate`, `superseded` - exactly one per close,
plus a required `--message` that is not blank. Three of them are free: they are
a word and a sentence. `completed` is the one with a precondition - it needs at
least one piece of evidence, `--commit`, `--test`, `--pr` or `--verified` - and
that precondition is the whole feature. Without it `completed` degrades back
into today's `closed` within a month and the field is decoration.

`duplicate` and `superseded` take an id instead, and imply the reason - the flag
carrying the value is a worse place to also have to name the reason. The id must
exist and must not be the issue itself, the same two checks `--blocked-by`
already makes, for the same reason: a dangling pointer in the one field whose
job is to point somewhere.

Evidence is a claim, not a proof. `--test` records the command; it does not run
it, and nothing here should. A tracker that shells out because a flag said so is
a different and much worse tool.

## Where the resolution lives

This is the decision the PRD hands us and it is not obvious, because the file
format is flat `key: value` and evidence is a typed repeatable list. The
frontmatter parser partitions on the first colon into a dict, so a key cannot
repeat; `labels` and `blocked_by` get around that by comma-joining, which is why
neither may contain a comma. A test command may. So the existing trick does not
stretch here and pretending it does is how we lose someone's `--test` string.

Three ways out:

1. A `## Resolution` section in the body. Best to read, and the body already
   round trips verbatim. But `--json` then needs the structure back, which means
   parsing prose we also let people hand-edit - a second parser, in the one file
   whose failure mode is silently writing a wrong dict over the description.
2. One frontmatter key per evidence type, comma-joined. Cheapest, and wrong on
   the first test command with a comma in it.
3. One frontmatter key holding a JSON array:
   `evidence: [{"type": "commit", "value": "81af03c"}]`.

Recommending 3. `partition(":")` keeps the whole rest of the line, so it round
trips through the existing reader and writer untouched, `json` is already
imported, no value is restricted, and the type survives - which is FR-16 and the
thing `--json` needs. It costs the one thing this project actually cares about:
that line is ugly in a file we promise reads fine without the tool. `issue view`
paying that back by rendering a real Resolution block is the deal, and it is
worth taking - the alternative is a Markdown parser we would have to trust with
the description.

`reason` and `closed_at` stay plain scalars beside it: they are single values,
they are what a filter would want later, and there is no reason to bury them.

## `issue set ISS-014 closed` has to stop working

That is US-012 and it is a breaking change, not a flag. It is documented in the
README, it is in the tests, and it is the muscle memory. Refusing it is still
right - a second door into closing means the evidence rule is advisory, and an
advisory rule is one an agent in a hurry routes around. The error names the
command to use instead. `set` keeps `open` and `in-progress`, so reopening stays
where it is.

Two things ride on that verb and must not be lost with it: the batch form (`set`
takes several ids, `close` reasonably takes one) and the `ISS-012 is now ready`
cascade that runs after a close and is currently in the middle of `set_fields`.
Whichever way `close` is wired - delegating to `set_fields` or lifting the
cascade out of it - one function decides what closing frees. Not two.

Old closed issues keep working untouched: no resolution keys, nothing rewritten,
`view` prints them exactly as it does now. Same rule as issues that predate
`priority` - absent is absent, and we do not invent a reason nobody gave.

## Reopening, and what we are not building

`issue set ISS-014 open` on a closed issue leaves the resolution keys alone;
`set_fields` only writes the fields it was asked for, so this is already true
and just needs a test that says so on purpose. Closing again overwrites them
with the new resolution.

Overwrites, not appends. The PRD leaves room for a resolution history and this
is the place to say we are not storing one: the previous resolution is in git,
`issue log ISS-014` already prints it, and that is the same answer this project
gives every time it is asked to keep history in the file. A list of resolutions
in frontmatter is an event log, and an event log in a Markdown file is a
database with no queries.

Also out of the first cut: `issue verify`, `issue context`, closing from a
commit message, any GitHub call, and validating a PR URL - the URL is a
reference we store, and network access must never be on the path to closing an
issue.

## Where it touches the code

New verb in `cli.py`, its function beside `set_fields` in `issues.py`, because
it is the same write with a different front door. Validation all of it before
the write, in one pass, the way `require_blockers` runs before anything is
touched - a close that fails must leave the file exactly as it was. Commit
existence is `git cat-file -e`, local only, and skipped rather than fatal when
there is no repo, which is how `log_issue` already treats git being absent.

`as_dict` grows a `resolution` object when the keys are there and omits it when
they are not - the rule `labels` and `assignee` already follow. `view` grows a
Resolution block under the table and above the body, with the evidence lines
typed. One resolution model, two renderings, same as `next`.

Tests: `tests/test_close.py` - each reason, the evidence rule, the two id
checks, the JSON shape, an old closed issue still rendering, and a reopen that
keeps its resolution.
