# The stability promise is prose with nothing enforcing it

ISS-051 wrote down the four things an outsider may depend on: the frontmatter
format, the `--json` shapes, the exit codes and the three env knobs. Nothing
in the suite asks whether they still hold.

They are not untested. Twelve test files exercise `--json` and nearly every
test asserts an exit code - but incidentally, on the way to checking a verb.
No test enumerates the documented key set, so dropping a key from `view`
passes green: every existing assertion reads the keys it cares about, and
none of them reads the ones it does not.

That distinction is the whole issue. Coverage of a surface is not a contract
over it. The contract is the enumeration, and the enumeration is exactly what
a stranger who pinned this version is relying on.

The README is the specification and it constrains the test as much as it
motivates it: `--json` shapes are stable in what they contain and not in what
they omit, every documented key is always present and empty rather than
missing, and new keys may appear. A test that fails on an added key would
contradict the promise it is guarding.

## Scope

`tests/test_stability_contract.py`, reading `tests/fixtures/`:

- every documented `--json` command, every documented key present, including
  on the empty result
- the exit-code contract: 0 for a filter matching nothing, 1 for a lookup
  finding nothing, 1 for a refused or partly refused write
- the three env knobs doing what README says they do
- an unknown frontmatter key surviving a rewrite

## Acceptance

- the test fails when a documented key is removed and passes when one is added
- it reads only `tests/fixtures/`, never this repo's own `.issues/` (ISS-049)
- one file, in `tests/all.py`, no framework
