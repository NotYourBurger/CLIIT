# Line endings: every write is LF, and the round trip can see it

The directory is already mixed. Measured at byte level today:

    .issues/ISS-031.md         61 CRLF, 0 bare LF
    .issues/work/ISS-031.md     0 CRLF, 71 bare LF

The tool writes through Python text mode, so on this machine `\n` becomes
`\r\n` on the way out; an agent editing a plan with its own tool writes LF.
No `open()` in src/ or tests/ passes `newline=`, and there is no
.gitattributes.

This is not hypothetical. ISS-031's plan records it: "the edit that was
supposed to fill it in had silently failed on CRLF line endings."

## The blind spot

`check.py:round_trip` reads in text mode, so universal newlines collapse
`\r\n` to `\n` before the comparison, and `join_file` emits `\n`. The two
sides match while the bytes on disk differ. The one module whose docstring
says "nothing else here can lose writing" cannot see the failure that already
happened.

## The fix

- `newline="\n"` on `storage.write_issue` and `plan.write_plan`. Reads keep
  universal-newline translation, so a hand-edited CRLF file still parses.
- `round_trip` reads with `newline=""` so the comparison is byte-honest.
- That makes the existing CRLF issue files findings. Normalise them once, in
  the same commit, with a throwaway byte-level `\r\n` -> `\n` pass. Not
  through `write_issue`, which would stamp a false updated_at on every one of
  them. No shipped verb: this happens once.
- Extend `test_encoding.py:unguarded` to require `newline=` on write-mode
  `open()` only. Same ast walker, same reason it exists - fail on the class,
  not on the fourth instance.

## Acceptance

- a CRLF round trip case in test_storage.py, beside the nasty body
- a CRLF plan-edit case in test_plan.py
- test_encoding.py fails on a new write-mode open() without newline=
- `issue check` silent, exit 0, after the normalise pass
- reads still parse a hand-edited CRLF file
