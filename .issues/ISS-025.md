# output order - the sections read bottom-up, the lines inside them do not

The terminal leaves the last line printed right above the prompt, which is
where the eye already is. So the most relevant line has to be the last one
printed, and this repo has said so twice already: `rank` orders `list`
least-urgent-last, and ISS-023 reversed `brief`'s sections for the same
reason.

ISS-023 stopped at the section boundary - its own comment says "order inside a
section is untouched". That was right for headers and wrong for rows, and the
result is a brief whose sections read up from the prompt correctly while the
lines inside four of them read down. Five renderings still put their most
relevant line furthest from the cursor:

```
$ issue brief
RECENTLY RESOLVED
ISS-024  issue handover ...          <- newest close, top of the block
ISS-022  Split issues.py ...
ISS-023  issue brief prints ...
ISS-021  issue brief - the ...
ISS-020  Evidence-based closing ...  <- oldest close
+19 more                             <- and this is what sits at the prompt
```

## The rule, once

**A header opens its block. The items inside it end with the one you came
for.** That is the whole change - ISS-023's half of it already holds, and
nothing about which issues are selected, which are capped, or what `--json`
emits moves at all.

Ordering and rendering stay separate, which is why this is a rendering issue
and not a sorting one. `ranked_actionable` must keep returning most-urgent
first: `next` takes `[0]` from it and `brief` slices `[:BRIEF_CAP]` off the
same head. It is the printing that reverses, after the cap, or the cap starts
hiding the wrong end of the list.

## The sites

- **`brief` READY** (`issues.py`, the `sections` list) - `ready` comes off
  `ranked_actionable`, most urgent first, and is printed that way. Inside one
  section this is exactly the arrangement `rank` exists to prevent: the row
  nearest the prompt is the one you should start last. `list` and `brief`
  disagreeing about which end of a list is urgent is worse than either choice.
- **`brief` RECENTLY RESOLVED** - `closed` is sorted newest-first by
  `closed_key`, so the oldest of the five is at the prompt. Reverse the five
  that survive the cap, not `closed_key` itself; `--json` keeps newest first,
  because a parser has no cursor.
- **`brief`'s `+N more`** (`render.py:omitted`) - it is appended, so after the
  rows reverse it would sit under the newest row and read as if it were
  hiding something newer. It summarises the tail that was cut, so it belongs
  at the top of its block, directly under the header.
- **`handover list`** (`handover.py:list_handovers`) - `load_handovers(id)[::-1]`
  puts the newest checkpoint at the top. The newest is the only one a resuming
  session usually wants, and it is the line furthest from the cursor. Drop the
  reversal: `load_handovers` already returns oldest-first, which is the order
  this wants. `--json` stays newest-first.
- **`handover latest` and `handover view`** (`render.py:handover_lines`) - GIT
  and FILES are appended after NEXT, so the cursor lands on a list of file
  paths while the one line the next session has to act on is above it. NEXT is
  last in `SECTIONS` for exactly this reason and then two blocks were printed
  past it. Move GIT and FILES up, between the header lines and SUMMARY - they
  are the state the checkpoint describes, and they read as context, not as an
  instruction.
- **`issue log`** (`issues.py:log_issue`) - `git log` is newest-first by
  default, so a long history puts the commit you care about off the top of the
  screen and the initial filing at the prompt. `--reverse` is the whole fix and
  it works with `--follow` (checked). The "not shown above" note on stderr
  stays correct as written.

## What is already right, and must stay that way

Named because each one looks like the same bug and is not, and a later pass
that "finishes the job" would make the output worse:

- **Table headers** (`render.py:print_table`) and the `HANDOVERS FOR <id>`
  line - a header labels the block it opens. This is ISS-023's rule and it
  holds.
- **The `ISS-024  title` line in `next_lines`** - that is the header of its
  block, not the first of four items.
- **`view`'s body, printed last** - you ran `view` to read the body. The
  metadata above it is the header, spelled long.
- **`close`'s "ISS-012 is now ready" cascade, printed last** - the whole point
  is that it is the next thing to do, and it already ends up at the prompt.
- **Every `--json` ordering.** A parser has no cursor and no screen. `--json`
  and the human rendering are allowed to differ here, and this is the one
  place they should - which is also why the reversal belongs in `render.py`
  and in the printing half of `brief`, not in the sort keys both renderings
  share.

## Tests

Almost every assertion needed is already written and currently asserts the
wrong direction, which is the cheapest possible version of this change:

- `tests/test_brief.py` pins the READY row order (`["ISS-002", ... "ISS-007"]`),
  `found["READY"][-1] == "+2 more"`, `RECENTLY RESOLVED[:2]` and its
  `"+1 more"` at `[-1]`. All four flip. The section-order assertions from
  ISS-023 do not - that half already holds.
- Add one assertion the file does not have: the same call with `--json` still
  gives READY most-urgent-first and `recently_resolved` newest-first. That is
  the check that stops the next person fixing this in `closed_key` or
  `ranked_actionable` and quietly changing which issue `next` picks.
- `tests/test_handover.py` pins `["H-007", "H-004", "H-002", "H-001"]` for
  `handover list` - flip it. Add that NEXT is the last line `handover latest`
  prints on a handover that has a git block, since that is the one this issue
  regresses if GIT moves back down.
- `tests/test_log.py` only ever makes one commit, so it cannot see order at
  all. It needs a second commit and an assertion that the first line is the
  older one.

## Not in this issue

Paging, `--reverse` flags to turn any of this off, and a terminal-height check
that only reverses when the output would scroll. The first two are a
preference for a decision this repo has already made once per command, and the
third makes the output depend on the window, which is the one thing that makes
it impossible to test.
