# read_plan and git both raise where their docstrings promise they cannot

Two functions document a no-raise contract, and neither keeps it. Both are on
recovery paths, which is the worst place for a traceback: the moment you need
the tool is the moment it stops working.

## read_plan says "Never raises."

It opens with `encoding="utf-8"` and no `errors=`, so one bad byte ends the
command:

    UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe9 in position 36

The whole design of `read_plan` is that the file's shape is not enforced -
unknown headings are ignored, a missing section is absent rather than empty,
and an unrecognisable file is noted on stderr and returned anyway, so that
`start` never reseeds over an agent's only copy. A decode error is the one
malformation it does not survive, and it is the most likely one: a truncated
write (ISS-038), an editor saving latin-1, a copy-paste through a bad terminal.

The cost is not just the traceback. `start` reads the plan before it reseeds,
so a plan that cannot be read is a plan that cannot be resumed - and `next`,
`view` and `close` all read plans too, which means one bad byte in one plan
takes out commands that had nothing to do with it.

## git says "None if it did not work"

`git()` in `plan.py` returns None on a non-zero return code and nothing else,
so when the binary is absent `subprocess.run` raises before it can:

    FileNotFoundError: [WinError 2] The system cannot find the file specified

The docstring is explicit that a git failure should cost the git block rather
than the output, and `git_context` repeats the promise. Both are true for a
directory that is not a repo and false for a machine without git - a container,
a stripped image, a PATH problem.

The same call is made in five other places without protection:
`fields.py:72`, `issues.py:1199` and `1214`, `validate.py:123` and `131`.
`require_commits` is the one that matters most: it already decides to skip
validation entirely when there is no repo, because "network access must never
be on the path to closing an issue" - the same reasoning applies exactly to git
not being installed, and it crashes instead.

## The fix

One `errors=` decision for reads of files this tool did not necessarily write,
and one `FileNotFoundError` catch in the shared `git()` helper, with the five
direct `subprocess.run` calls routed through it rather than each catching for
itself.

For the decode: surfacing a repairable file beats both crashing and silently
mangling it. Report the path and what to do about it.

## Acceptance

- a plan with invalid UTF-8 does not raise; the path is named on stderr and the
  issue's own output still prints
- `start` does not reseed over a plan it could not decode
- every git call degrades to the documented absent answer when git is missing
- `issue close --commit` behaves the same with no git binary as with no repo
- an issue's output survives the loss of its optional git context
- tests for both, with a planted bad byte and with git removed from PATH
