# Every write truncates first, so a failed write erases the issue

`write_issue` opens the target with mode `w`, which truncates before a single
byte of the new content is written. The content is already built in memory by
then, so the window is small - but anything that stops the process between the
open and the flush leaves the file empty, and an empty file is not a short
issue, it is no issue at all.

Measured on a 5160-byte issue with the write made to fail:

    before: 5160 bytes
    write raised: disk full
    after:  0 bytes
    parses back as: None

Not a hypothetical: a full disk, a killed terminal, a laptop lid, or a crash in
any of the code between the two lines produces it. The prose in the body is the
part with no other copy - it is why this tool exists - and git only helps if the
issue happened to be committed.

`write_plan` in `plan.py` has the same shape. Its blast radius is smaller,
because `start` seeds once and never reseeds, but a 0-byte plan left behind is
worse than none: `read_plan` returns a plan, so `start` will not reseed over it,
and the checkpoint list is gone with no way to get it back.

`append_event` is already safe by construction and should stay as it is - it
appends and never rewrites, which is the property this issue wants everywhere.

## The fix

Write to a temporary file in the same directory, flush it, then `os.replace`
onto the target. `os.replace` is atomic on both POSIX and Windows, so a reader
sees either the whole old file or the whole new one and never a partial. Same
directory because a replace across filesystems is not atomic.

This belongs in one place. Every issue write already goes through
`write_issue`, and that is also where the clock is read, so the durable-write
rule should live beside it rather than in each caller.

## Acceptance

- a write that fails part-way leaves the previous file byte-for-byte intact
- the same guarantee covers `write_plan`
- the bytes written are unchanged: UTF-8, LF, and `join_file`'s exact output
- no temporary file is left behind on either the success or the failure path
- a test that injects a failing write and asserts the original survives
