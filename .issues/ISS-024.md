# issue handover - carry a session's context to the next one

An issue says what the work is. It does not say where the work currently
stands, and that gap is paid for once per session: an agent picks up
`ISS-042 / in-progress`, re-reads the repo, re-derives the decisions the last
session already made, and rediscovers the constraint that changed the
approach. All of that existed - in a conversation that is gone.

PRD: `docs/PRD/04-Session-Handover.md`.

```
issue handover create ISS-042 --summary "..." --next "..."
issue handover latest ISS-042 [--json]
issue handover list ISS-042 [--json]
issue handover view H-006 [--json]
```

A handover is the delta a session produced: what changed, what was learned,
what remains, where to resume. It is append-only, it never touches issue
status, and it is written by hand - no LLM, no transcript, no diff. The same
budget `brief` is held to: useful context per token, not information per
token.

## Handovers are not small issues

The failure mode is a handover that restates the issue - problem, acceptance
criteria, priority - and the next session reads two copies of one thing and
trusts the staler one. So the split is a rule, not a style note:

- The **issue** is the durable definition. It is edited.
- The **handover** is a checkpoint in that issue's execution. It is never
  edited; a correction is a new handover.

Which is also why `create` does not set `in-progress`, does not claim, and
does not touch `blocked_by`. A session blocker (`--blocker "no Windows box"`)
is prose about why this session stopped. `blocked_by: ISS-014` is the project
dependency graph. The first must never write the second - `in_the_way` stays
the only thing that decides what blocked means.

## Where the fields go, and why

Frontmatter has no list type, and `done`, `remaining`, `decisions`,
`discoveries` and `blockers` are all lists of free-text sentences. Sentences
have commas in them, so the comma-joined trick that `labels` and `blocked_by`
use is out - it would cut a decision in half at the first clause.

`evidence` bought its way out of that with a JSON line, and CLAUDE.md calls
that the one ugly line in a file we promise reads fine without the tool. Five
more JSON arrays of prose would spend that promise entirely, on the one
artifact whose whole contract is that a human can read it in a diff.

So the rule is the split the content already has:

- **Frontmatter is what the tool computed**: `id`, `created_at`, `issues`,
  `git_branch`, `git_head`, `git_dirty`, `files`. Every one is short, and
  none can contain a comma except `issues` and `files`, which are ids and
  paths - the same shape `set_field` already reads back.
- **The body is what the session said**: `## Summary`, `## Done`,
  `## Remaining`, `## Decisions`, `## Discoveries`, `## Blockers`,
  `## Resume At`, `## Next` - prose under a heading, `- ` bullets for the
  lists. This is the PRD's own sketch, and it is a file worth opening.

That buys the human-readable half and costs a body parser: `## Heading` to
section, `- ` lines to list. It must round trip - a section written by the CLI
and read back must be the same strings - and it must survive a hand-edited
file, because the PRD promises manual editing stays possible. `test_storage.py`
already guards the issue body with a deliberately nasty one; the handover body
needs the same treatment and for the same reason: a parser bug here does not
raise, it silently drops a decision.

## What has to move in storage.py first

`parse_issue` requires `status` and `title`, and a handover has neither.
`write_issue` forces `updated_at` on every write and hardcodes
`.issues/<id>.md`, and a handover is append-only and lives one directory
down. None of that is reusable as it stands, and writing a second frontmatter
reader beside it is how the two start disagreeing about what a `---` means.

So: lift the format itself out of the issue-shaped wrapper. One function that
splits a file into `(fields, body)` and one that joins them back, staying
exact inverses; `parse_issue` becomes that plus its required-key check, and
`write_issue` becomes that plus `updated_at` and the path. The handover reader
and writer are then the same two functions with a different wrapper. One
implementation of the file format, which is the property `test_storage.py`
exists to defend.

`next_id` needs the prefix as an argument rather than only from
`ISSUE_PREFIX`; handovers allocate `H-NNN` against `.issues/handovers/`.
ponytail: a repo that sets `ISSUE_PREFIX=H` gets ids that look alike in two
directories - they cannot collide on disk and `handover view` only ever
searches one of them, so this stays a naming oddity rather than a bug.

## Ordering, and the one thing `latest` must not do

`latest` is a lookup: exactly one handover, exit 1 when there is none, same
contract as `next` and `view`. It must not be "the last file `listdir`
returned" - sort on `(created_at, id)`, the way `closed_key` already breaks
its tie down to the id, so two calls in a row cannot name different
checkpoints. `list` is that same sort reversed, newest first, one line each.

Git is read at creation and stored, never recomputed at read time - a
handover describes the tree as it was, and a `latest` that re-shelled out to
git would quietly rewrite history every time it was called. Read-only, and a
git failure loses the git block rather than the handover: outside a repo the
command still works, because the context is worth recording either way.

## Where it touches the code

The layers from ISS-022 are the whole point here and the new code should land
in them rather than beside them: `storage.py` gets the format primitives,
`validate.py` gets "summary and next are required and non-blank" and "every
referenced issue exists", `render.py` gets the human and `--json` renderings,
and `handover.py` is the new module holding what a handover is - read, write,
allocate, order. `issues.py` gets `view_issue` printing the one-line reference
from US-018 and nothing else; `cli.py` gets a `handover` sub-app.

Validation runs before anything is written, so a `create` naming a missing
issue does not burn an `H-` id - the rule `create_issue` already follows.

Tests: `tests/test_handover.py` - required summary and next, a blank one
rejected, multi-issue creation discoverable from every id named, `latest`
after three handovers with the same timestamp, exit 1 with no handover and
with an unknown `H-` id, a session blocker leaving `blocked_by` alone, status
unchanged after a create, the body round trip including a `## ` inside a
bullet, and `--json` shape with every optional list present and empty.

## Not in this issue

`issue brief` surfacing handovers, `issue context`, promoting a decision into
permanent memory, and the freshness warning that compares recorded HEAD to
current HEAD - the PRD lists all four as future extensions and they stay
that way. Also out, and named in the PRD's own non-goals: automatic creation
on session end, transcript or prompt storage, diffs, source snapshots, and
any agent-specific integration. The command is invoked deliberately, by a
person or an agent that decided the context was worth keeping.
