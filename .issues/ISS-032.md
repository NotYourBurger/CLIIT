# issue check --plans - measure plan-keeping, not commit cadence

ISS-031 wrote a threshold down before the numbers were known: if fewer than
three of the next five plans show more than one commit, the work plan is
deleted the way the handover was. Its own Discoveries section then recorded
why that number cannot answer the question - it counts commits, and this
workflow commits the plan edits at the end, so every plan on disk reads
`1 commit` while every one of them was in fact edited repeatedly.

A kill switch wired to a sensor that measures the committer will delete a
feature that works. Fix the sensor before the threshold is judged.

## The signal

Content, not history - so it survives a fresh clone (which mtime does not) and
a squashed commit (which the count does not).

`read_plan` already parses every section. A seeded-and-abandoned plan is
exactly: no checkpoints, and `decisions`, `discoveries`, `current` and `next`
all empty. That is the whole test, and it needs no git.

- `plan_rows()` carries an `untouched` fact per row.
- `plan_cells()` renders it as a leading state beside the existing ticked
  count.
- The two git columns stay, demoted from verdict to context. They are not
  wrong, they are insufficient.

## The threshold

Restate it against the new signal in docs/PRD/05-Work-Plan.md, and record why
the commit count was retired. ISS-031's whole point was writing the number
down before the result was known; swapping the instrument without rewriting
the number quietly throws that away.

## Acceptance

- a plan that is only the seed is reported as untouched
- all six plans currently on disk report as touched - they are 7/7 to 9/9 ticked
- no new git call: the signal comes from read_plan alone
- --plans still exits 0 and still honours --json
- the threshold in docs/PRD/05-Work-Plan.md names the new signal
