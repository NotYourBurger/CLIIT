# issue brief - the project's state in one command

`issue next` answers "what do I do now" and deliberately answers nothing else.
The question before it - "what is going on here at all" - still costs five
calls: `list`, `list --ready`, `list --blocked`, `list in-progress`, then a
read of whatever closed recently. A person entering the repo after a month
runs them and skims. An agent runs them, pays for four tables it mostly
discards, and reconstructs a state that was already sitting on disk.

PRD: `docs/PRD/03- Issue-Brief.md`.

```
issue brief           # what is happening in this project
issue brief --json    # the same orientation, for an agent
```

Read-only, one load of `.issues/`, exit 0 - orientation always succeeds, even
in an empty project. That is the split from `next`: `next` is a lookup and
exits 1 when it finds nothing; `brief` is a report and an empty backlog is a
finding, not a failure.

## It must not become a second opinion about project state

This is the whole risk in the feature and it is worth naming first. Every
number and every section here already has a function that decides it:
`select_issues` loads, `in_the_way` blocks, `is_ready` and `actionable` say
what can be started, `next_rank` orders, `resolution_of` reads a close. If
`brief` re-derives any of them - even one inlined `status == "open" and not
blockers` - then `issue next` and `issue brief` can disagree about which issue
is next, and the day they do, the brief is worse than the five calls it
replaced, because it is confidently wrong instead of verbose.

So: `next` in the brief is `min(candidates, key=next_rank)` over
`actionable`, the same two lines `next_issue` runs, and the ready list is that
same sorted list with the head dropped. Not "the ready filter, sorted somehow
similar". If that means lifting those two lines into a small function both
call, lift them - `next_issue` printing and `brief` printing are two
renderings of one decision, which is the arrangement `view`/`--json` already
has.

## The sections, and why each earns its space

Ordered by what a caller does with it, not by what is easiest to compute:
summary, next, in-progress, ready, blocked, recently resolved, warnings.

- **Summary** is five counts - open, in-progress, ready, blocked, closed. It is
  the cheapest thing in the brief and the only part that says how big the
  project is, which is the thing that tells you whether to trust the truncated
  sections below it.
- **Next** is one issue. Not three: the point of `next` is that the tie is
  already broken.
- **In-progress** is uncapped, and is the only uncapped section. Work already
  started is the thing you most want to not start again, and a project with
  fifteen in-progress issues has a problem the brief should show rather than
  hide behind `+10 more`.
- **Ready** is five, minus the next issue if it is in there, plus `+N more`.
- **Blocked** shows each issue with its direct blockers and their statuses -
  `said_blockers` already prints exactly that string.
- **Recently resolved** is five, most recent first, with the close message
  when there is one. This is the section that makes the brief project memory
  rather than a dashboard: it is where an agent finds out that the thing it
  was about to build was closed as `not-planned` last week.
- **Warnings** is blockers pointing at ids with no file. `blocker_status`
  already returns `missing` for them and `in_the_way` already refuses to let
  them block anything; the brief is the first place that says out loud that
  the graph has a hole in it.

Empty sections are omitted in the human output and present-but-empty in JSON.
A human reading a blank `BLOCKED` header learns nothing; a parser branching on
whether a key exists learns worse than nothing.

## Sorting the closed ones

`recently resolved` needs an order and the file has two candidates:
`closed_at`, written by `close_issue`, and `updated_at`, written by every
write. `closed_at` is the honest one and it is absent on every issue closed
before ISS-020 landed. Fall back to `updated_at` for those, and do not
backfill: absent stays absent, and an approximate date on a legacy file that
looks exactly like a recorded one is the kind of quiet lie this format is
supposed to make impossible. Then id, so the order is total and two calls in a
row cannot disagree.

## What it is not

Not a summary of anything. No issue bodies, no full dependency graph, no
complete closed list, no acceptance criteria, no source scanning, and
absolutely no LLM anywhere near it - the brief is what an agent reads before
it starts thinking, and something that has to think to produce it is a
different feature with a different failure mode.

The budget is `useful context / tokens`, not `information / tokens`. Every cap
in the section list above is there because an unbounded brief on a 300-issue
repo is the backlog dump the caller was trying to avoid, and at that size the
command quietly stops being worth running.

Also out: `--budget`, architecture sections, session handover, and
`issue context` - the PRD lists them as future extensions and they stay that
way. The brief points at where to look next; it does not load it.

## Where it touches the code

New verb in `cli.py`. In `issues.py`, one `brief()` beside `next_issue`, built
on one `select_issues()` call and one `by_id` - the loads are the cost here and
there is no reason to pay them twice. The data is assembled once and rendered
twice, human and JSON, so the two cannot drift; issue objects in the JSON are
`as_dict`, not a new shape invented for this command.

Tests: `tests/test_brief.py` - the section order, the caps and their `+N`
lines, the next issue not appearing twice, `brief` and `next` naming the same
id, an empty project exiting 0 with valid JSON, a missing blocker showing up
as a warning, and a legacy closed issue with no `closed_at` still placing in
the resolved list.
