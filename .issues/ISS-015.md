# Labels - what kind of issue is this

Status says where an issue is, priority says when to do it, and nothing says
what kind of thing it is. `bug`, `frontend`, `backend`, `auth`, `docs`,
`performance`, `ai` - the words people already put in the title because there
is nowhere else to put them.

```
issue create "Login broken" "..." --label bug --label auth
issue create "Title" "Description" -l bug -l auth
issue list --label bug
issue set ISS-014 --label backend
```

## The whole lifecycle, in one issue

Priority went in as create-only and immediately needed a second pass to become
settable. Labels do not get that excuse - a label is added late by definition,
because you learn what an issue is about after filing it.

1. **Create** - `--label` / `-l`, repeatable, none by default
2. **Read** - visible in `view`, and in `list --json`
3. **Filter** - `issue list --label bug`
4. **Add** - `issue set ISS-014 --label backend`, alongside a status or a
   priority in the same write
5. **Remove** - the part that has no equivalent in status or priority, and the
   reason this issue is bigger than the last one. See below.

## Storage

Frontmatter is flat `key: value` lines - `parse_issue` splits on the first
colon and keeps the rest as a string. A list has no representation there, and
inventing one means touching the one function in this codebase that can
silently lose your writing.

So: `labels: bug, auth`, one string, split on commas at the edges that care.
No labels means no field at all, not an empty one - the same rule as the issues
that predate `priority`, where missing stays missing.

A comma is therefore a delimiter and cannot be in a label. Reject it at create
and set time rather than writing a file that reads back as two labels. Strip
whitespace and lowercase while we are there: `Auth` and `auth` are the same
label, and finding that out later means two half-populated tags.

Unlike status and priority there is no closed list to validate against - the
point of labels is that the user invents them. The only rules are the shape
ones above.

## Removal

`--unlabel auth`, repeatable, pairs with `--label` in the same call. A leading
minus (`--label -auth`) loses to it because click reads `-auth` as a flag, so
the one that reads nicely in a README is the one that needs quoting to work at
all; and "edit the file" is not an answer for the field people will change most
often. Adding and removing the same label in one call is refused rather than
resolved. Removing the last label removes the field.

## Where set_fields gets harder

`set_fields` currently computes `changed` by comparing the wanted value against
what is on disk, and reports only what actually moved. That works because
status and priority are single values that replace.

Labels do not replace, they merge - and `set ISS-014 --label backend` on an
issue that already has `backend` must land in the "already" branch, not print
that it set something. So the wanted set is computed per issue, and the
comparison defaults a missing field to the empty string, so "no labels" and
"removed the last label" are the same state and not a write.

## Decisions

**A LABELS column in `list`: yes, last, and only when something has labels.**
Filing labels you cannot see while scanning the list is the failure mode worth
avoiding. Putting the column last means the one column with no bound on its
width has nothing to push off the screen, and skipping it entirely when no
issue has labels keeps the table as it was for anyone not using them. This
turns the hand-threaded column widths into one `COLUMNS` table.

**Two labels on one filter: AND.** `issue list --label bug --label auth` means
both. Every other filter in this tool narrows when you add to it - a status
plus a `--priority` is an intersection - and a flag that widened the result set
would be the odd one out. On `create` the same flag still means "and also",
which is the same idea from the other side: the issue gets both.

**`--json` splits them: yes.** `"bug, auth"` makes every consumer redo the
split, and the whole point of `--json` is that a script does not have to parse
what the human output shows. Labels come out as an array; that is the one place
the JSON stops being a literal transcript of the frontmatter, and it is worth
it. Issues with no labels have no key, matching the file.
