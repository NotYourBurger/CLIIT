# Issue ownership - who is working on it

`issue list --ready` answers "what can I start right now", and it gives every
caller the same answer. Two agents ask within a second of each other, both get
ISS-021 at the top, both start, and the most useful query in the tool is also
its best generator of duplicate work. A person is no better off: nothing in any
file says someone already picked it up, so the polite thing to do is ask in
chat, which is the coordination the tracker was supposed to hold.

Status is close but is not this. `in-progress` says the stage the work is at,
not whose it is - and it is exactly the field that goes stale, because the
person who set it is the person who stopped thinking about it.

```
issue claim ISS-021 --by tahmid      # mine, if nobody else got there first
issue claim ISS-021                  # --by defaults to you
issue assign ISS-021 --to codex-1    # hand it over, no questions
issue release ISS-021                # not mine any more
issue list --assignee tahmid         # what tahmid is on
issue list --unassigned              # what nobody has taken
issue list --ready --unassigned --json   # what an agent may safely start
```

## The whole lifecycle

1. **Claim** - `claim`, with a precondition: it succeeds only if the issue is
   unassigned, or already yours. Claimed by someone else is exit 1 and nothing
   written.
2. **Assign** - `assign --to`, with no precondition. It force-sets the owner,
   because handing work over is a normal thing to do and a tool that makes you
   release first is a tool people work around.
3. **Release** - clears the field. Already unassigned is success, the same way
   `set` treats a field that is already what you asked for.
4. **Store** - one field, `assignee`, one name, on the issue.
5. **Read** - `--assignee` and `--unassigned` on `list`, a column when anything
   is owned, a row in `view`, and the field in `--json`.

## A field, not a label

`issue set ISS-021 -l tahmid` almost works today, and that is the trap. Labels
are a set: nothing stops two of them, and two labels named after two people is
the duplicate-work bug wearing a hat - it records the collision instead of
preventing it. Ownership has an arity, exactly one, and "exactly one" is the
entire feature. A field can hold that rule; a set cannot.

It is also the wrong shape for filtering. `--label tahmid` mixes people into the
same namespace as `bug` and `auth`, so `issue list --label auth` starts
returning rows because someone is named after a subsystem.

## Who "me" is

`--by` and `--to` take a name, and the name is a string this tool does not
verify. It cannot: an issue is a file in a git repo, anyone who can write the
file can write any name into it, and a tracker that pretends otherwise is
lying in its own frontmatter. The audit trail already exists and is better than
anything invented here - `issue log ISS-021` shows who committed the change.

So `--by` is optional and defaults to `$ISSUE_USER`, then `git config
user.name`. The environment variable is the knob this tool already has, twice
over, and it is what an agent sets once at the top of a run rather than
threading a name through every call. With neither available, `claim` says so
and exits 1 rather than writing an owner nobody can be held to.

## Three verbs, one write

`claim`, `assign` and `release` are the first fields to get commands of their
own instead of a flag on `set`, and only one of them earns it. `assign` is
`set --assignee codex-1`, `release` is the same write with an empty value; they
are spellings, and they should be that literally - one function that writes the
field, three ways in. Two write paths for one field is how the "already
assigned" message and the real behaviour drift apart.

`claim` is the one that is genuinely different, because it is not a write, it is
a write with a condition attached. Everything else in `set` wins by definition:
you asked for high, it is high now. `claim` can fail while being perfectly well
formed, and that is a different contract, worth a different word.

`--assignee` should exist on `set` too, so the field behaves like every other
field for anyone who has already learned `set`. It is the same call `list`
made when it accepted `--status` as a second spelling.

## The race the feature exists to lose gracefully

Check-then-write is not atomic. Two agents claim the same unassigned issue in
the same moment, both read "unassigned", both write, and the second one wins
silently - which is precisely the duplicate work this was built to stop, now
with a frontmatter field agreeing that everything is fine.

There is no lock to take and there should not be one. Write, then re-read the
file, and if the assignee that comes back is not the name you claimed with, you
lost - report the owner who won and exit 1. Whichever order the two writes land
in, exactly one of them re-reads its own name, so exactly one caller is told it
succeeded. It is three lines and it turns a silent double-start into one agent
picking the next row instead.

ponytail: that closes the window, it does not remove it - a reader interleaved
between another writer's two operations can still be told the wrong thing, and
the fix if it ever matters is an `O_EXCL` claim file, not a lock.

## Blocked, closed, and other people's work

A closed issue cannot be claimed: there is nothing to start, and a claim on it
is almost always a typo'd id that happens to exist. Exit 1, say it is closed.
`assign` and `release` still work on one, because cleaning up after the fact is
real - and because `assign` is the verb with no preconditions, and adding one
here would make that untrue in exactly one place.

A blocked issue *can* be claimed. Claiming is saying you will do it, which is
the reasonable thing to do about work you are waiting on, and refusing would
repeat the mistake ISS-017 argued out of: a tracker that refuses is one people
stop telling the truth to.

Not in scope, deliberately: claim setting `in-progress` as a side effect - two
facts written by one word, and then `release` has to guess whether to undo it.
Also out: multiple assignees, reviewers, teams, and expiring a stale claim after
N days. The last one is tempting and is a scheduler, not a tracker.

## What it looks like

An ASSIGNEE column, conditional the way LABELS is - absent entirely when nothing
in the result is owned, so a repo that does not use this does not pay a column
for it. Before LABELS, because LABELS is last on purpose: it is the one value
with no bound on its width, and a name has a bound.

That is now the second conditional column and the fourth field that is stored,
filtered, shown and written by `set`. The field table ISS-016 named and ISS-017
reached for again is this change, or it never happens.

`view` gets a row in the table like the others. Unassigned shows as `-`, the
same as a missing priority, because the reader is scanning a column and an empty
cell reads as a rendering bug.

## Agent experience

`issue list --ready --unassigned --json` is the whole loop: find work nothing is
blocking and nobody owns, `claim` one, and the claim is what makes the next
agent's query return something different.

- `--assignee` and `--unassigned` AND with every other filter, and with each
  other they contradict - that is exit 1 with a sentence, not an empty table,
  because no repo state can satisfy it and printing "no issues" blames the repo
  for the caller's mistake.
- `assignee` in `--json` when the issue has one and absent when it does not, the
  same rule labels follow. `blocks` and `ready` are always there because nothing
  stores them and the consumer cannot derive them cheaply; `assignee` is stored,
  and for stored fields the JSON stays a transcript.
- Exit codes are the contract: 0 for a claim that is now yours, including one
  that already was, 1 for a claim someone else holds and 1 for a closed one. The
  conflict message names the current owner on stderr, because the next thing the
  caller does is either pick another issue or go and ask that person.
- `claim` prints one line, id first: `ISS-021 is now tahmid's`.

## Where it touches the code

`set_fields` already builds `fixed` from status and priority - the fields that
replace rather than merge - and `assignee` is a third one. The add/remove
machinery labels and blockers need does not apply, which makes this the cheapest
of the four fields to store and the most expensive to name.

`select_issues` takes two more filters, and unlike `--ready` and `--blocked`
both are decidable from a single issue, so they go back inside the loop where
status and priority live.

`print_table` grows its second conditional column, and the rule that decides
which columns appear stops being an `if` about LABELS.

The re-read in `claim` is the first time this tool reads a file it just wrote.
`write_issue` returns the path already, and `parse_issue` is right there.

## Open

Should `release` refuse to clear someone else's claim without `--force`? It is
the same argument as `claim`, one verb over, and the same answer is not obvious:
taking work off a person who has gone home is normal and needing a flag for it
is friction, but so is losing your claim to someone else's fat-fingered id.
Leaning no flag, on the grounds that `assign` is already the unconditional verb
and `release` is just `assign` to nobody - if that is true, they should behave
the same, and this question answers itself.
