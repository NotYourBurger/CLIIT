# issue next --claim - take it, and retry when the claim is lost

ISS-027 narrows the window. It does not close it: two agents who both see the
same unassigned issue still collide, because reading is not taking.

`--claim` is opt-in, so `next` stays read-only by default. That contract is
load-bearing - asking what to do next must not decide it for you, and that is
what makes it cheap to ask twice - so this is a flag and never the default.

The point is the retry. `claim_issue` closes its race by reading the file back
and letting exactly one caller see its own name; the loser is told to go and
pick another row. An agent calling `next --claim` has already asked for that
row, so losing must walk to the next candidate rather than exiting - a
`--claim` that fails is worth no more than the `next` it replaced.

- extract `try_claim(id, who) -> bool` from `claim_issue`, which keeps its
  messages and its exit codes
- `next_issue(as_json=False, claim=False)` walks `candidates` in order and stops
  at the first claim that lands
- candidates exhausted is exit 1, `search`'s contract as before

## Acceptance

- `--claim` writes the assignee and returns that issue
- a second `--claim` as another user returns the next issue, not an error
- N calls under N users yield N distinct ids
- plain `next` still writes nothing - asserted, not assumed
- `tests/test_next.py` covers each
