# issue start - the work plan replaces the session handover

An issue says what the work is. A handover was meant to say where the work
stands - written at the end of a session, by hand, as a deliberate act. The
end is the problem. A session usually stops at a usage limit, a crash or a
closed terminal, and none of those pause to write anything. The evidence is on
disk: this repo shipped `issue handover` in ISS-024 and has twenty-five issues
and zero handovers.

So stop treating the record as an ending. Make it the thing the work already
runs on: a **work plan** created before the first edit and ticked as each
checkpoint lands, so it is never more than one checkpoint behind the truth.

PRD: `docs/PRD/05-Work-Plan.md`, superseding `04-Session-Handover.md`.

```
issue start ISS-002 [--anyway]
issue next            # now carries plan state and live git
issue view ISS-002    # now carries a compact plan block
```

```
Issue       what needs to be achieved
Work plan   how this session is currently achieving it
Git         what actually changed
```

## The plan is not a handover with a different name

A handover was append-only because it was a claim about a moment. A plan is
mutable because it is a claim about now, and `git log --follow` is still the
audit trail for how it changed - the same answer this repo already gives for
issues. One plan per issue, at `.issues/work/ISS-NNN.md`, with `## Goal`,
`## Plan` (`- [ ]` checkpoints), `## Decisions`, `## Discoveries`, `## Current`
and `## Next`.

The checkpoints are recoverable units of progress - `Login UI`, not `Open
auth.py` / `Add import` / `Save file`. Three to ten per issue. That is
guidance in the workflow rule and not a validated constraint: a tool that
rejects an eleventh checkpoint is wrong about a large issue, and an agent
correctly stops maintaining a list that has become noise.

## The CLI seeds, the agent edits

`issue start` writes the skeleton. Nothing in the CLI mutates the plan after
that - the agent flips `- [ ]` to `- [x]` and appends prose with the editing
tool it is already holding.

The rejected alternative was a verb per mutation: `plan check 3`, `plan note`,
`plan next`. Every one of those is a shell round trip in the middle of the
work, which is a decision point, which is a place to skip. Ticking a box has
to be cheaper than not ticking it or it does not happen - and "it does not
happen" is the entire bug being fixed here.

The cost is that nothing enforces the file's shape, so the reader is built not
to need it: `split_sections` recognises the known headings, preserves unknown
ones, treats a missing section as absent rather than empty, and never raises.
Absent means absent, the call `priority_of` already makes.

## `start` is also resume

`issue start ISS-002` refuses a blocked issue - exit 1, blockers named on
stderr, nothing written - and `--anyway` proceeds and notes them in the plan
header. Otherwise it sets `in-progress`, claims as `ISSUE_USER`, and seeds the
plan. If a plan already exists it prints it instead of reseeding.

That idempotence is the point. An agent that first has to work out whether
work exists will sometimes work it out wrongly, and the cost of being wrong is
the plan. One command covers both situations, so the workflow rule has one
line where it would otherwise have a branch.

`in_the_way()` stays the only thing that decides what blocked means.

## "Keep working" is `issue next`

`next_rank` already sorts `in-progress` above `open` and breaks every tie down
to the id, so `next` already names the right issue deterministically. It just
does not say what was happening there. It gains the plan's `Current`, `Next`
and unchecked checkpoints, plus live branch, HEAD and dirty files - and stays
read-only, because asking the question still must not answer it.

Git is recomputed at read time and never stored. The handover stored it
because a handover was immutable and a stored fact could not go stale. The
plan is live, so a stored HEAD would be a lie the moment anything committed.

## The rule has to reach the agent twice

`issue init` writes the nine-line workflow rule into `CLAUDE.md` / `AGENTS.md`,
and the seeded plan carries a condensed reminder as an HTML comment. One
constant in the source, two renderings, or they drift.

Line 8 of that rule - **do not wait until the end of the session to record
progress** - is the behavioural guarantee the whole feature rests on, which is
why it also lives in the plan file. A rule at the top of `CLAUDE.md` is the
first thing a long session compacts away; the plan file is on disk and is
re-read every time the agent touches it.

## What comes out

`handover.py`, its four verbs, `tests/test_handover.py` and the README section
go. `split_sections` / `join_sections` / `git_context` move down a layer and
keep their tests - they were the good parts and the plan reads through them.
`issue view`'s handover line becomes the plan block. Nothing else referenced
handovers, and no handover exists on disk, so there is nothing to migrate.
`04-Session-Handover.md` stays in `docs/PRD/` as the record of the shape this
replaces.

`issue close` gains one stderr line naming unchecked checkpoints, and closes
anyway. A checkpoint that stopped being relevant must not be able to veto a
close, and the acceptance criteria already own completeness. The plan file is
not moved or archived - it stays in `work/` as the account of how the issue was
actually built.

Net: four verbs deleted, one added.

## Known risk, on the record

Nothing enforces this. A seeded plan that is never ticked is worse than no
plan - it is confidently stale and the next agent believes it. What changes
the odds is that the plan is created before the work instead of after it, is
edited with a tool already in hand, and carries its own instructions. But the
guarantee is still a sentence in a file, and the last sentence in a file
produced zero handovers. If it fails again the answer is a hook, not a longer
sentence.
