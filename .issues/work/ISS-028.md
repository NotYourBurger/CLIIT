# ISS-028 Work Plan

## Goal

issue next --claim - take it, and retry when the claim is lost

## Plan

- [x] README

## Decisions

- `try_claim` rechecks every precondition itself rather than trusting the
  caller's earlier read; `claim_issue` keeps all the messages and exit codes.
- `--claim` with no configured name exits 1 before walking anything, so it
  cannot half-succeed.
- A landed claim re-reads the file before rendering, so `--json` shows the
  assignee it just wrote.
- Candidates exhausted gets its own sentence ("taken while trying") - exit 1
  either way, but the repair is different from an empty backlog.
- `try_claim`'s two guarantees are tested in test_assignee.py, next to `claim`'s
  own checks, not in test_next.py: they are facts about the write, and `next
  --claim` is one of its two callers.

## Discoveries

- `next_issue` already filters candidates with `claimable_by` when a user name
  is configured, so the retry walk only ever revisits rows this user could take.
- Mutation-testing the new checks found two holes that the green suite hid:
  deleting `try_claim`'s read-back, and deleting its `claimable_by` recheck,
  both left every test passing. Neither caller can reach the recheck today -
  which is the argument for the test, not against the code: without it the
  write overwrites an owner read a moment earlier and the read-back then
  confirms the theft.
- Staging the lost race needs a stand-in for `set_fields`; two processes
  interleaving is not arrangeable from one script.
