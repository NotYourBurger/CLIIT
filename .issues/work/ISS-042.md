## Decisions

- The filename is what separates a broken issue from a stray note. `parse_issue`
  returns the same None for both and that skip is load-bearing, so the shape
  check (`storage.ID`) on the name is the distinction, exactly as the issue
  said.
- `parse_issue` split into `parse_fields` + `missing_fields` rather than
  check.py re-deriving the required-key test. A second copy of that rule is a
  report that disagrees with the parser, the same reason `FIELD_ORDER` has one
  copy.

## Discoveries

- The issue text is one step out of date: ISS-039 already made an unparseable
  file a finding. What is left is that the message does not name the missing
  field, and that it fires on a stray note too - the acceptance criterion the
  current code fails. Confirmed on a planted directory: `notes.md` is reported.
- The other three are silent exactly as described.
- `cycle_from` finds the same cycle from every member, so the walk reports it
  from the lowest id in the path and nowhere else - three lines for one cycle
  is a report that gets skimmed.
- The evidence check also requires a `type` key, not only an object: every
  reader indexes `item["type"]`, so an array of bare objects is a KeyError one
  `issue view` away, which is the same defect the criterion is about.
