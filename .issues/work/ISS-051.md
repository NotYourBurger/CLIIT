# ISS-051 Work Plan

Nothing says which shapes a stranger may depend on

## Decisions

- **The policy goes in README.md, not a new `docs/STABILITY.md`.** README is
  already the user-facing spec this repo keeps in sync; a second file carrying
  the same kind of prose is the ISS-045 mistake with a different name.
- **The file format is declared stable and another tool may read and write
  `.issues/*.md`.** Anything else makes "the files are the database" a slogan.
  Written with the write rules attached — one printable line per value, no
  comma in `labels`/`blocked_by`, `evidence` a JSON array, UTF-8 and LF — so
  the permission is usable rather than a shrug.
- **No `format_version` key.** Unknown-key preservation is already the forward
  compatibility a version key would buy, so it stays unbought until the format
  changes in a way preservation cannot absorb. That is the acceptance
  criterion read literally: the policy says stable, so no key.
- **The `--json` shapes are stable in what they contain, not in what they
  omit.** Keys may be added; names and types do not move, and every documented
  key is always present. That is exactly what the code already promises in
  `as_dict`, `brief` and `check` — three separate comments saying a consumer
  must not branch on whether a key exists.
- **The exit codes are covered**; the human tables, the stderr prose,
  `.issues/work/` and the Python modules are explicitly not.
- **No new frozen corpus.** ISS-049 already froze `tests/fixtures/` and
  `issue check` already reads it, so the mechanism this policy needed exists.
  A published conformance suite waits for the first outside tool that asks
  for one.

## Discoveries

- The work plan and event log had to be named as *not* covered. Their readers
  are documented as never raising and as tolerating unknown headings and
  unknown event types, which is a promise about the reader, not about the
  shape — the opposite of the issue format, where `issue check` enforces one.
