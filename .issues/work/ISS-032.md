## Decisions

- `untouched()` lives in plan.py, not check.py: it is defined against `seed`,
  which is plan.py's, and putting it there keeps `SECTIONS` from leaking up.
- The state column goes immediately after the id rather than beside `ticked`.
  The issue says "leading state"; leading the row is the position that reads as
  the verdict, which is exactly the demotion the two git columns are getting.
- The words are `touched` / `untouched`, straight from the acceptance criteria,
  rather than a verdict word like `kept` / `abandoned` - the row reports what
  the file shows, and whether three of five is enough is the reader's call.
- `goal` is excluded from the test because `seed` writes it from the issue
  title. Including it would make every plan touched and the signal dead.

## Discoveries

- `split_sections` strips each section, so an empty heading reads as `""` and
  the whole test is falsiness. No emptiness rule of its own to write.
- Before the change, all seven rows read `1 commit` or `2 commits` while the
  six finished plans are 5/5 to 9/9 ticked - the exact miscalibration ISS-032
  was filed for, visible in one command.
- The test's literal-line assertions (`"ISS-901  1 commit "`) broke the moment
  a column was added, because every column is padded to its widest value and
  `untouched` is nine characters. Added a `cells()` helper that splits a row on
  runs of two spaces, so an assertion is about its columns and not about what
  else happens to be in the report.
- The acceptance criterion "all six plans on disk report as touched" is not
  asserted in the suite: it would fail the moment somebody runs `issue start`
  and has not written anything yet, which is a correct state. Verified by
  running the command instead, and the output is in the close message.
