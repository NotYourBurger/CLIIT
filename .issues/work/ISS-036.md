## Decisions

- Reread the agent-behaviour report (docs/agent-behaviour-report.md) and the
  issue text before designing: the losses were the claim-race stdout, the
  kill-time plan snapshot, the killed worker's first tool calls, and turn
  counts - all things a *coordinator* running probes against a specific issue
  would want to record as they happen, not something the single-agent
  workflow already covers. Treating it as a real product feature (matches the
  `ax` label pattern of ISS-026/027/031/032/035) rather than throwaway
  experiment scaffolding.
- One JSONL file per issue at `.issues/work/<ID>.events.jsonl`, sibling to the
  plan. Append-only (open in "a" mode, one write per call) so a killed process
  can never corrupt an earlier entry, and JSON-per-line survives free-form
  multi-line text (probe stdout, a plan snapshot) without a second body-parser
  like `split_sections`. A new file next to the plan rather than a new section
  inside it: the plan is edited by hand with the tool an agent is already
  holding, mid-thought; events are appended by a running process, often not
  an agent at all (a shell probe, a coordinator's kill hook), and mixing the
  two would put a machine-appended fact in the middle of prose someone is
  mid-edit on.
- `issue event <ID> TEXT` appends; `issue event <ID>` with no TEXT prints the
  log back (human table, `--json` for the array) - so the feature is usable
  without leaving the CLI, but the raw file stays one `cat` away by design,
  the same call the plan already made.
- `--stdin` reads TEXT from stdin instead of the argument, so a coordinator
  can pipe a probe's real stdout or redirect a plan snapshot
  (`issue event ISS-033 --type snapshot --stdin < .issues/work/ISS-033.md`)
  without a shell-quoting problem.
- `--type` is a free label (`probe`, `lifecycle`, `snapshot`, default `note`),
  not a closed vocabulary - the reader tolerating an unknown type is the same
  call `read_plan` already makes about an unknown heading.

## Discoveries

- `check.py` already had the exact shape of this problem twice - "everything
  wrong with the files" and "an artifact with no issue beside it" for the
  work plan - so extending its one loop over `work/` to also recognise
  `.events.jsonl` cost one branch and one new import, not a second scan.
- Manual end-to-end run confirmed the full loop: append with `--type`,
  `--stdin` piping multi-line probe output, reading it back plain and
  `--json`, and `issue check` catching both a hand-appended malformed line
  and an event log left behind after its issue file was moved away.
