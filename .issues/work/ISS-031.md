## Decisions

- `--plans` is a report, not a check: it prints on stdout and exits 0. The
  threshold in ISS-031 is a human decision taken once after five issues, not a
  condition the tool can fail on, and `check`'s exit code means "these files
  are wrong". So `--plans` takes the whole verb rather than adding findings.
- Every plan is reported, closed issues included, in id order. The threshold
  counts plans, so filtering to in-progress ones would throw away the rows it
  needs. Whether a stale count matters is the reader's call, which is what the
  status column in `issue list` is already for.
- The two git columns are dropped rather than filled with a placeholder when
  git cannot answer - the call `git_context` already makes, and the ticked
  count needs no git so the row still says something.
- The table is built in check.py, not render.py: check.py already prints its
  own findings, and one table does not earn a second module hop.
- `--json` is honoured in plans mode. Not because a script wants it yet, but
  because `check --plans --json` silently printing a human table is a trap,
  and the branch is three lines.

## Discoveries

- **This counts commits, not edits, and today those are very different.** The
  baseline: ISS-026, 027, 028 and 030 all read `1 commit`, and every one of
  them was in fact edited repeatedly during the work - the edits were just all
  committed together at the end. So the number under-reports a kept plan and
  cannot, on its own, tell "seeded and abandoned" from "kept and committed
  once". Before the threshold is judged, either the plan gets committed as it
  is ticked, or the measure has to change. Written down here because ISS-031's
  whole point was to fix the number before the result was known.
- The report caught a real one on its first run: this plan showed `0/0 ticked`
  because the edit that was supposed to fill it in had silently failed on CRLF
  line endings. A count nobody keeps is exactly what this exists to find.
- `read_plan` notes a shapeless plan on stderr, so `--plans --json` can have
  both a clean stdout and a non-empty stderr. That is the right split - it is a
  diagnostic, not a row - and the test asserts it rather than asserting silence.
