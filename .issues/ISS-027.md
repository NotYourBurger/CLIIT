# issue next - do not hand the same issue to two agents

`claim` already says who may take an issue: unassigned, or already yours. `next`
does not read that field at all, so two agents with different `$ISSUE_USER` are
promised the same id - and `next_rank` breaking every tie down to the id is what
guarantees it. The determinism that makes `next` safe to ask twice is the same
property that makes it collide.

The rule exists; `next` just does not use it.

- `fields.py` gains `claimable_by(issue, who)` - no assignee, or the assignee is
  `who`. One predicate.
- `claim_issue` drops its inline owner check for it. Same behaviour, one opinion,
  which is the arrangement `in_the_way` already has.
- `next_issue` filters its candidates through it, and only when `current_user()`
  returns a name: a solo user with no `ISSUE_USER` and no git name must not be
  told there is nothing to do.

The filter goes in `next_issue` and not in `actionable()`. `brief` shares
`ranked_actionable` and orientation has to keep showing other people's work -
what is going on here is a different question from what may I start.

Nothing left because it is all someone else's is exit 1 with its own line:
`Nothing to work on - N issue(s) are assigned to someone else` is a different
repair from every issue being closed or blocked.

## Acceptance

- assigned-to-another is skipped, assigned-to-me and unassigned are returned
- no name configured means no filtering
- every candidate assigned elsewhere is exit 1, empty stdout, the distinct message
- `brief` output is unchanged
- `tests/test_next.py` covers each
