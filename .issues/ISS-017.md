# Issue dependencies - what blocks what

Sixteen issues, and the one you picked up cannot start until another one lands.
Nothing in the repo records that. The tracker knows what each issue is, its
status, its priority and its labels, and nothing at all about ISS-012 being dead
in the water until ISS-009 ships. That fact lives in someone's head, or in a
sentence in a body that no command can act on.

Priority answers "what matters most". It does not answer "what can I start right
now", and on a team of eight those are different questions - the highest
priority open issue is very often the one nobody can touch.

```
issue set ISS-012 --blocked-by ISS-009   # ISS-012 cannot start until ISS-009 closes
issue set ISS-012 --unblock ISS-009      # never mind
issue list --ready                       # open, and nothing open is in the way
issue list --blocked                     # stuck, and what on
issue view ISS-012                       # both directions, each with its status
issue list --ready --json                # what an agent picks up next
```

## The whole lifecycle

1. **Declare** - `--blocked-by` (`-b`) on `set`, repeatable, the same shape as
   `--label`. `--unblock` (`-B`) removes one, the way `--unlabel` does.
2. **Store** - one field, `blocked_by`, on the issue that is stuck. One side of
   the edge only; the other direction is derived.
3. **Refuse** - an unknown id, a self-link or a cycle is an error before
   anything is written, and the cycle error prints the path.
4. **Read** - `--ready` and `--blocked` on `list`, both directions on `view`,
   both in `--json`.
5. **Report** - closing the last blocker says what it just unblocked, on the
   same run that closed it.

## One side of the edge, not two

"A blocks B" and "B is blocked by A" are one fact. Store it twice and the first
hand-edit, deleted file or half-finished write leaves the two copies
disagreeing, with nothing able to decide which is true - and this is a tracker
whose files people are invited to edit by hand. Store `blocked_by` on the
blocked issue and derive `blocks` by reading the others, which `list` and
`search` already do on every run.

The blocked issue is the right side to keep it on. The dependency is a property
of the thing that cannot proceed, so "why can I not start this" is one file
read. It also degrades in the right direction: delete the blocker and the stuck
issue still says what it was waiting for, where the opposite arrangement loses
the fact entirely and silently.

## Ready

`--ready` is open, with every id in `blocked_by` closed. That single query is
what the whole feature exists for - the standup question, the "what do I pick
up" question, and the one an agent asks before it does anything.

Direct blockers only, not transitive. If A is blocked by B and B is blocked by
C, and someone closed B while C was still open, then B is done because a person
said so, and B's blockers stopped being A's problem at that moment. Walking the
chain past a closed issue second-guesses a decision that was already made, and
prints "ISS-003 is blocked by ISS-021" for two issues whose files do not mention
each other.

Missing ids do not block. An id whose file has been deleted can never be closed,
so counting it would leave an issue stuck forever with no way out except hand
editing the frontmatter. It shows as `ISS-042 (missing)` everywhere ids are
printed, which is louder than a wrong "blocked" and points at the actual repair.

## Blocked is not forbidden

`issue set ISS-012 in-progress` on a blocked issue prints what is in the way, on
stderr, and then does it. A tracker that refuses is a tracker people stop
telling the truth to: the first time it is wrong about a dependency, someone
deletes the field rather than argue with it, and a graph people route around is
worse than no graph.

Not in scope, deliberately: parent/child epics, "relates to", "duplicates",
cross-repo links and a rendered graph. Blocking is the one relationship that
changes what you do next. The others are bookmarks, and the body text is already
a fine bookmark.

## Cycles

A blocked by B blocked by A means neither is ever ready, and nothing ever says
why - `--ready` just quietly returns one row short forever. That is the failure
mode worth spending code on, and it is cheapest at write time, when the graph is
one edge away from valid.

Print the path, not "cycle detected": `ISS-012 -> ISS-009 -> ISS-004 -> ISS-012`
tells you which edge to drop. "Cycle detected" sends you off to read four files.

## What it looks like

No new column. A blocked row gets the line underneath it that `search` already
prints for a match - `blocked by ISS-009 (open)`, indented under the row - and
that is deliberate twice over: two columns with no bound on their width cannot
both be last in the table, and ids plus their statuses are exactly the shape
that does not fit in a cell.

It shows on plain `issue list` too, not only under `--blocked`. A blocked row
that looks identical to a ready one is the precise failure this issue exists to
fix, and hiding it behind a flag means the default view keeps lying by omission.
`--ready` is the filter that takes them away.

`view` shows both directions, each id with its status, because a blocker's
status is the only thing about it that matters:

```
Blocked by: ISS-009 (open), ISS-004 (closed)
Blocks:     ISS-020 (open)
```

## Agent experience

An agent's entire job here is "what should I do next", and `issue list --ready
--json` is that in one call.

- `--json` grows `blocked_by` and `blocks`, both arrays of ids, and `ready`, a
  boolean. Arrays for the reason labels became one: nothing downstream should
  have to split a string the tool already split. `ready` because recomputing it
  means an agent re-reading every file to check each blocker's status, when the
  tool had them all in memory a moment ago.
- `blocks` is in the JSON although no file stores it. That is the second place
  the JSON stops being a transcript of the frontmatter, after labels, and the
  reason is the same: the consumer wants the fact, not the storage.
- Exit codes stay what `list` and `set` already promise. A filter matching
  nothing is exit 0 and a sentence - `No ready issues` - because it is a fact
  about the repo, the distinction ISS-016 drew against `search`. An unknown id,
  a self-link and a cycle are exit 1, one message, nothing written, the same
  contract a bad priority word has today.
- The unblocked report is stdout, one line per issue, id first: `ISS-012 is now
  ready`. An agent that just closed something picks up the next thing without a
  second command, and `awk` gets the id from where it always is.
- `--ready` ANDs with `--priority` and `--label` like every other filter, so
  "the most important thing I can actually start" is one command and not a
  pipeline.

## Where it touches the code

`blocked_by` is the second comma-joined set field after `labels`. `labels_of`
and `clean_labels` are that pattern with a label-shaped validator hard-coded in
the middle; splitting the set handling from the per-value check is the change,
and it is the third time this codebase has reached for the field table ISS-016
already named.

`select_issues` takes status, priority, labels and a query. `--ready` and
`--blocked` are two more filters with one difference worth naming: they cannot
be decided from a single issue. They need every issue in hand to look up each
blocker's status, so they filter after the load rather than inside the loop.

`print_table` already takes a notes map, which `search` fills with the line a
match came from. The blocked line is the same mechanism with different text,
which is why this adds no column.

`set_fields` already merges instead of replacing for labels, so `--blocked-by`
and `--unblock` are the same add/remove pair - plus the validation labels do not
need, because a label is invented and an id must exist.

Closing is the one write with consequences in other files. After `set` writes,
whatever it closed may have freed something, and finding out is the same scan
`list` does.

## Open

Should `--blocks` exist as the mirror flag, so `issue set ISS-009 --blocks
ISS-012` records the edge from the end people usually say it from? It reads the
way the sentence is spoken. It also means a command naming one id writes a
different file, which nothing else in this tool does. Leaning yes, as a second
spelling that lands in the same single stored field - the same call `list
--status` made for `search`.
